# P4 — Task→Work Session dentro del DAG con recibo físico tipado (17-10-2026)

## Sección ejecutable, solo rama aislada

`WholeSourceLightExecutor._execute_dependent_graph` admite ahora, de forma acotada, una operación Tasks START seguida de una operación Tasks STOP que refiere a **la sesión concreta recién creada**. No se deduce el ID de un pronombre ni se selecciona la sesión activa por casualidad. La topología exige por separado: (1) antecedente Core físico que demuestra la Task existente, (2) un START en Tasks referido a ESA Task, (3) un STOP posterior con su propio enlace a la Task Core **y** un enlace al texto de la sesión creada por ese START. Un STOP con varios padres arbitrarios, una cadena Task→Task distinta de START→STOP, dependencia Core→Core o Task multiobjetivo sigue **fallando cerrado**.

Antes del primer WRITE, Router propone agrupación, la auditoría independiente debe atestiguar todos los bytes y aristas, cada fragmento Tasks pasa por su TaskInterpreter/Temporal y el auditor de fuente `exactly_one_operation`, y cada acción tiene sus dos revisores de Task objetivo. La arista específica START→STOP pasa por `verify_session_dependency`, dos revisores independientes y un contrato JSON que exige `one_session` y `same_session` con citas literales de origen, sin IDs. El dominio Tasks `validate_task_batch_prewrite` admite una transición START→STOP SOLO si la transición exacta fue prevalidada; dos START simultáneos, un STOP sin evidencia o cambios de índices siguen vetados.

Durante la ejecución el Core Writer existente materializa sus facts y links canónicos. En START el adaptador de producción consume **el `WorkSessionMutationResult` verdadero** del `TaskWorkSessionService.start`, guardándolo solo dentro de la petición; `prove_created_session` lo ata al ID real de Session, a la Task y a los hashes actuales del Markdown y raíz actor-local. Si falta la evidencia después de un WRITE, la excepción deja E3 bloqueado para que no haya reintento ciego. Para STOP se revalida Core→Task y la Session E2 privada y se pasa el ID y los tokens de CAS del recibo al **mismo** `TaskWorkSessionService.stop` existente. Si la sesión o la Task cambiaron antes del STOP, devuelve `needs_attention` y el agregado es `partial`, con recibo E3; si una caída ocurre después de la escritura física del STOP pero antes de completar el recibo, la claim E3 permanece `unresolved_attempt` y bloquea duplicados. No hay nueva implementación de Writer ni un segundo repositorio de conocimiento.

## Transporte hasta el gráfico del navegador

La revisión final encontró una pérdida real del dato: el Runtime N:M estaba mostrando solo el primer antecedente y enviaba `depends_on: null` en rutas independientes, una forma que el validador estricto de `odyssey_web/client.js` ya rechazaba. Se corrige el **contrato compartido**, no la maqueta: los grupos sin relación omiten `depends_on`/`reason`; los grupos dependientes llevan `depends_on` con índice anterior y `reason: null`; cuando hay M antecedentes verificados también transportan `dependency_indices` con TODOS los ordinales en su orden, de forma acotada y única. El frontend valida fuente, índices anteriores, pertenencia del índice principal, cardinalidad y duplicados; una referencia futura/inventada invalida el flujo. `odyssey_web/progress.js` muestra las dos relaciones («Depende de los caminos 1, 3») en vez de atribuir solo la Task o solo la Session. `tests/odyssey_web_client.test.mjs` y `tests/odyssey_web_progress.test.mjs` comprueban render real y rechazos; las rutas históricas 1→1 siguen mostrando una sola dependencia. La ruta de producción de `workflows/odyssey-online.ts` también se ha actualizado para rechazar arrays de índices adulterados. `tests/p4_dependent_n8n_flow_contract.mjs` sigue validando Core→Tasks 1:1 con el formato corregido, y el nuevo `tests/p4_n4_n8n_flow_contract.mjs` consume **el recibo del runtime Python físico** y lo pasa por `safeFlow`/`flowMatchesStages` del workflow instalado y `validateExecutionFlow` del cliente. Todos los índices Core y Session sobreviven de Python a JS, sin afirmar que se haya desplegado n8n. `execution_ledger` conserva su dependencia primaria de compatibilidad y no se utiliza para inventar relaciones extra.
