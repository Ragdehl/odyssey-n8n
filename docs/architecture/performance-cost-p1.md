# Performance / Latency / Cost P1 — measurement and decision contract

Status: **P1A deterministic observability and one P1B isolated DEV baseline are complete on Draft PR #125.** P1C has one evidence-backed recommended target but is not authorized or implemented. The [Functional Roadmap](functional-roadmap.md) owns current status and order.

## Objective and sequence

Answer where an end-to-end request spends time, which individual provider calls cost money, how often and why Luna falls back to Sol, how much input each call receives, and which measured contributor is the best first optimization. Provider time and Odyssey overhead must be distinguishable before choosing a change. No universal latency SLA is set before baseline evidence.

1. **P1A — observability completeness:** preserve existing bounded evidence, close only diagnosis-blocking gaps, and freeze the cases, environment, pricing snapshot, and report format.
2. **P1B — baseline and bottleneck diagnosis:** run the approved synthetic DEV cases and identify dominant latency, cost, fallback, and input-token contributors. Record unavailable values honestly.
3. **P1C — one optimization:** select exactly one primary target from P1B evidence. This contract does not authorize its implementation now.
4. **P1D — before/after verification:** rerun the same frozen cases and semantic oracles with enough repetitions to distinguish a change from provider variance, within a separately approved budget.

## Fallback and input-size diagnosis

For each planner attempt report `planner.luna` or `planner.sol_fallback`, model, reasoning, outcome, elapsed time, supplied input/output/cache/reasoning counters, estimated call cost or `unavailable`, and bounded failure category. Luna's current `RequestPlanningError` grouping is too broad to distinguish incomplete provider response, malformed JSON, local structural validation, and semantic fail-closed validation in the user-facing projection. P1A should reuse existing safe codes where available and add a small safe classification at the Luna boundary where absent; do not persist exception messages, prompts, raw responses, or hidden reasoning. A safe `ESCALATE` becomes clarification and is not Sol fallback. Count fallback rate by eligible fresh requests and by frozen case class, with numerator, denominator, and incremental Sol time/cost. Do not infer a general rate from seven distinct cases alone; repetitions or a later bounded sample are needed.

The planner prompt is not just user text: Sol renders fixed safety/semantic instructions, dynamic retrieval and writable schema capabilities, optional bounded recent conversation, and a strict output schema. Luna inherits that prompt and adds its first-pass rules and teaching examples, plus its own strict schema. Therefore the prior observed ~11–12k planner input tokens are a **hypothesis trigger**, not evidence of waste. First use provider-supplied per-call `input_tokens` and `cached_input_tokens`. If input size is a material cost/latency contributor, derive component byte/character lengths at render time for fixed instructions, capability projection, conversation context, request text, teaching examples, and structured-output schema. Such lengths are explanatory proxies; they must not be labelled token counts or stored with content. Avoid a new tokenizer or telemetry store for P1.

## Cost contract

Usage counters are provider observations when returned, while all dollar amounts are **estimates**, not billing facts. The n8n product workflow uses the dated snapshot at `benchmarks/phase20_answerer/pricing_snapshot.json` (currently `2026-09-07`) injected at workflow render time. It prices `input_tokens - cached_input_tokens` at ordinary input rate, cached input at cached rate, and output at output rate; reasoning tokens are already within output tokens. The current calculation requires valid input, cached-input, and output counters plus a known model rate, and rejects cache-write tokens other than zero. Missing usage or an unknown rate makes the whole request `unavailable`, never zero. Luna and Sol fallback calls are enumerated independently; contextual resolver, writer, fact selector, and the n8n answerer are included when their call records and required counters survive projection. No billed invoice reconciliation or billing API is in scope.

P1A should expose an additive per-call estimated-cost breakdown beside the existing request total, with the same pricing date/source/version identity and no parent-stage double count. A stage subtotal is derived from its child calls. If one chargeable call has missing usage, report that call's cost and the **complete** request total as `unavailable`; optionally show a clearly labelled known-call subtotal. Verify the deployed DEV pricing snapshot matches the frozen baseline snapshot before collecting evidence. Existing `OperationalStage.estimated_cost_usd` is present in the Core type but is not populated or projected today; do not assume it is an existing cost breakdown.

## P1A deterministic measurement implementation

The authoritative server-side outer interval is `operational.product_execution_duration_ms` in runtime HTTP: from immediately before `execute_product` (or intelligent `notes`) through its returned response object. For Chat it includes actor resolution, the serialized product lock wait, replay lookup, conversation context, Core, index refresh, response serialization, and delivery-result persistence when applicable. It excludes inbound HTTP body parsing/validation and outbound JSON writing. `operational.total_duration_ms` remains the smaller Core plus index-refresh interval. The browser's `browser_product_duration_ms` spans its product `fetch` through response JSON parsing; this includes n8n, network and proxy transit but excludes conversation-turn persistence before and after the product call. It is a separate clock on a different machine: use only compatible nested intervals or a labelled residual, never subtract it as a precise n8n measurement. The n8n answerer interval starts at routing and ends at response validation, including n8n scheduling and HTTP transport; it is not pure provider service time. Its stage is outside the Core total and has no Core-relative offset. Browser, Cloudflare and n8n sublayers remain unallocated.

```text
browser product wall (client clock; separate boundary)
  runtime HTTP product execution (server clock; separate boundary)
    Core total + index refresh
      planner
        planner.luna attempt [input_build, provider, parse, validate]
        fallback_decision (only when applicable)
        planner.sol_fallback attempt [input_build, provider, parse, validate]
      action.retrieve / action.write [one stage per action]
        get_context / preflight / reference_render / unit[i].materialize
        embedding.query[i] / embedding.documents[i]
        contextual_resolution / writer / fact_selector [one record per call]
      git / pending / index_refresh
  answerer (n8n HTTP-leg estimate, after Core; separate clock)
```

The Notes intelligent branch carries its own planner attempts and `notes.query` under a Notes operation total; its page transport now preserves bounded operational evidence. Other read-only Notes operations are outside the P1 baseline and have no new inner tracing. Bulk write internals, trivial local validation, dataclass construction, and UI rendering remain aggregated. A dominant residual inside one of these boundaries is a measurement gap to resolve before optimization, not evidence that the boundary is cheap.

Each parent and child has a monotonic wall interval and relative start offset where both share the same clock. Coverage is the **union** of known child intervals divided by parent wall time. `unattributed_ms = parent wall − child union`; overlap is reported separately and never double-counted. Negative, nonfinite or out-of-parent intervals yield unavailable coverage. Do not sum a parent with its children. P1B may name a measured child as the dominant contributor only when the compared parent has valid coverage of at least 90% and that child also has at least 90% coverage if its internals are the proposed optimization target. Below that threshold, the residual is itself a candidate bottleneck; report no finer optimization conclusion until it is measured or a later explicit review accepts the uncertainty. Root Core coverage, runtime HTTP wall, and browser product wall must each be reported under their exact boundaries; no universal performance SLA follows from this measurement rule.

Planner attempts retain ordinal, model, reasoning, duration, provider status, available input/cache/output/reasoning usage, parse status, result kind, validation stage/code, and safe failure category. The safe taxonomy is provider/API exception class, incomplete/timeout status, empty output, malformed JSON, invalid result envelope, local structural/semantic validation code, and unsupported result. Existing `PlannerValidationStage` and `PlannerValidationCode` values are reused where present. A completed provider call followed by failed local validation remains visibly different from provider failure. No prompt, response body, unrestricted exception message, or hidden reasoning is retained. The input-size proxy records UTF-8 bytes of fixed instructions, capability projections, recent context, current request, Luna rules/examples, and output schema when assembled; provider `input_tokens` remains the authoritative token total. Byte components are explanatory and must never be presented as exact token counts.

The exact disposable case registry is [`benchmarks/performance_p1/cases.json`](../../benchmarks/performance_p1/cases.json), version 1: R1 simple READ, R2 recent-context READ, W1 single WRITE, W2 two-person WRITE, W3 three-person narrative WRITE, C1 unintelligible fail-closed clarification, N1 intelligent Notes search. W2 and W3 prohibit cross-assignment of facts; C1 requires zero actions and no mutation. Cases must run from equivalent synthetic fixtures with fresh request identities. No unsupported kinship, group, backlink or relational semantics are baseline oracles.

The provider-free test oracles include Luna-only `¿Dónde trabaja Marta?` yielding one valid attempt, and the same request with Luna's locally invalid empty selection query (`SELECTION / EMPTY_QUERY`) followed by a valid Sol fallback. Fake clocks prove separate 3,104 ms and 4,191 ms attempts, order, usage, parent time, and retained failure code. Other deterministic tests prove repeated embedding spans, interval union/overlap/residual, malformed timing rejection, bounded transport, and pre-call budget refusal. The diagnostic report formatter prints independent attempts, child intervals, total/residual coverage, dated per-call estimates where usage supports them, and `unavailable` otherwise.

The original USD 0.20 whole-run worst-case reservation was a conservative benchmark guard, not an Odyssey product contract. The human deliberately retired it because normal-path capacity was not bounded enough to certify every theoretical execution and that proof was blocking the actual diagnostic objective. The provider-free `BudgetGuard` and pricing tests remain as reusable safety code, but are **not** a gate for this authorized baseline. ## Historical product-bound review

The human authorized reviewed **normal-path** bounds where they preserve intended behavior; the authorization does not supply numerical product limits. The 12 human-reviewed Luna/none answerer cases used 38–55 output tokens, but those cases intentionally cover compact answers rather than a detailed synthesis of several notes. The prompt requires grounded conversational answers and contains no length maximum. **8,192 total generated tokens** (including JSON and any reasoning tokens) is a candidate with over 140× headroom over observed Luna output, but there is no approved product expectation that a valid multi-note synthesis must fit it. No answerer cap has been implemented pending that decision. If approved, an incomplete provider response must fail closed; it must never present a truncated answer as complete. The provider's own 128,000-token hard limit is the current upper bound.

The validated Chat planner supports multiple independent actions and multiple write units; historical deterministic tests exercise five actions and the P1 narrative case needs three distinct people. Those are examples, **not** a product maximum. An arbitrary note-count cap would reject a supported request for every matching note in a larger vault. A fail-closed pre-mutation cap would preserve mutation safety but still change the product contract. Numerical action, unit, fact, and bulk-note limits therefore remain open; no such limit has been added.

Input bounds have the same open product question. The stack has no trusted exact model tokenizer wired for all payload/schema overhead. No input cap or approximate-token claim has been added. Any future reviewed limit must be checked on the exact rendered payload before provider invocation and must fail closed without partial mutation.
