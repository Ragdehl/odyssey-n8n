# P4 — Operaciones independientes Core + Tasks, fuente original y trazabilidad (16-10-2026)

**Ámbito:** solo rama experimental `feat/light-router-poc-20261016`, vault temporal, SELF sintético, sin instalar código en DEV/PROD ni tocar datos personales. La única autoridad del estado vigente sigue siendo `functional-roadmap.md` (primer bloque activo).

## Contrato incorporado

Una nueva puerta E2 read-only `odyssey_core.independent_source_scopes.verify_independent_source_scopes` admite un número variable de partes (2–16, presupuesto explícito) únicamente si la propuesta del primer modelo y la revisión **independiente** del segundo afirman que (1) todos los caracteres originales, incluidos espacios y conjunciones, se conservan exactamente una vez y en orden, (2) hay al menos una operación Core y otra de Tasks y (3) cada parte se entiende SIN tomar prestado un sujeto, fecha, persona, pronombre, objeto, Work Session o tarea de las demás. Ni la revisión ni el Router producen Note IDs, hechos canónicos o permiso de escritura. Un fragmento omitido, repetido, invertido, un campo adicional, una dependencia o un dict malformado provoca bloqueo sin escribir. No hay patrones para nombres, verbos o ejemplos del corpus.

La ruta productiva opt-in `odyssey_runtime.whole_source_light` usa este contrato cuando el Router propone `separable` y scopes explícitos Core/Tasks sin dependencia. Cada parte vuelve a pasar por **su propio Router, revisor completo, autoridad Core o intérprete Tasks y servicio de escritura ya existentes**. El Router secundario debe declarar solamente la capacidad revisada para esa parte; no se permite que una hipótesis introduzca un tercer servicio por accidente. Todas las partes comparten el **mismo reloj de recepción** del mensaje original, evitando cruces de medianoche.

Se mantiene el claim E3 exterior para toda la petición. Cada suboperación tiene locator estable `-independent-N`; un replay del request ID completo recupera el recibo exterior sin ejecutar otro Writer. Si un fragmento posterior falla antes de sus escrituras, los anteriores quedan marcados como **partial** en el recibo, no se anuncia éxito completo ni se borra el efecto físico. Si hay fallo incierto postwrite, el outer claim se conserva y se prohíbe un segundo intento automático. No hay atomicidad multi-documento, compensaciones inventadas ni reconciliación de claims sin prueba.

La respuesta ahora agrupa las etapas operativas reales por scope y añade `execution_flow` v1 compatible con el contrato de flujo de n8n: `application.router` observado, routes en orden, source scopes originales, estado real y los nombres exactos de las etapas que cada dominio emitió. Nada de etapas o respuestas de modelos inventadas. El refresco final general de índices sigue siendo un evento exterior a las rutas. Las pruebas comprueban correspondencia route↔stage y proyección de `project_execution_ledger`. Esto **no** sustituye inspección del gráfico real de chat o donut en navegador.

## Límites de seguridad y siguientes dependencias

1. **Operaciones dependientes Core + Work Session, Task UPDATE, subtareas con vínculos introducidos en el mismo mensaje:** no cubiertas por el contrato de independencia. Deben recibir un handoff E2 con evidencia canónica y permiso E3, no un split heurístico ni transformarse falsamente en Task CREATE. El camino Core existente sí soporta hechos + Task CREATE cuando se verifican sus dependencias.
2. **Recuperación E3 tras crash postwrite:** a falta de manifest físico prewrite y pruebas de lectura posterior, un claim sin recibo continúa bloqueando un nuevo write. Es intencional.
3. **Rendimiento:** sigue habiendo ~4 s sin GPT ni FastEmbed para 1000 Notes por validaciones repetidas dentro de Core; no declarar solucionado.
4. **Acceptance real:** navegador autenticado → webhook n8n aislado → P4 → GPT → Writer/Markdown → índice → n8n → UI, revisando gráfica, donut, transcript al salir/volver, acciones desde Notes y subtareas. No se ha realizado, ni se ha desplegado nada. La Raspberry tenía ~1,5 GB de swap ocupado; no se levantó otro navegador/n8n que pudiera afectar los servicios existentes.

El gate compartido `scripts/odyssey_cross_surface_gate.py` incorpora esta nueva familia de pruebas y el ledger `docs/architecture/odyssey-acceptance-contracts.json` vincula sus invariantes a tests concretos. Los resultados numéricos más recientes deben confirmarse en el roadmap tras ejecutar el gate y la suite global. **P4 NO está autorizada para DEV ni PROD.**

## Sondeo adversarial de dependencias con IA real

`scripts/p4_independent_scope_dependency_probe.py` (solo llamadas a proveedor, sin vault ni mutaciones) ejecutó tres mensajes sintéticos con anáfora o relaciones semánticas entre Core y Tasks. Los tres quedaron como **no separables**: contacto mencionado y siguiente llamada (`joint`, Core+Tasks+Temporal), persona mencionada y nueva Work Session para su presentación (`joint`, Core+Tasks+Temporal), Work Session ligada a un encuentro (`joint`, Tasks+Temporal). Resultado **3/3 no splits peligrosos** en esta muestra. No prueba que toda frase dependiente futura se detecte correctamente; no usar como argumento para activar el split sin la segunda revisión.

## Telemetría real, sin perder el resultado anterior

Se detectó que el agregador ad-hoc P4 perdía parte de la telemetría y detalles cuando el último subresultado pertenecía a Tasks. La nueva ruta mixta reusa `odyssey_runtime.routing._aggregate`, que renumera acciones y conserva estados, pending, history y IDs. El reporte `execution_flow` v1 transporta solo las etapas que devolvió cada dominio, con su nombre auténtico, sus índices originales, el source scope y su estado; `application.router` se mide **antes** de ejecutar los scopes (no con la duración de toda la petición). Runtime añade `index_refresh` al final y las pruebas distinguen correctamente ese stage global de los fragmentos E2. Aún falta comprobar `safeFlow` visual en n8n instalado y grafos; no suponer que el navegador ya muestra el recorrido íntegro.
