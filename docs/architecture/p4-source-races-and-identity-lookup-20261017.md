## 2. Comprobaciones tardías de integridad (carreras interproceso)

Antes, `CoreIndexedQueries` verificaba el inventario al INICIO de la consulta SQL; una modificación externa durante la consulta podía hacer que devolviera una negativa falsa. Ahora verifica de nuevo el **snapshot físico completo** tras realizar la selección/re-grounding, tanto si hay positivo como si no. No devuelve una prueba de ausencia si otro editor creó/modificó una nota en el intervalo; el Writer/CAS mantiene el control de escritura. El coste extra corresponde a un `scandir` de metadatos, no a releer Markdown globalmente.

`ContextIndex.rebuild` comprueba todos los paths+versiones de origen **después** de proyectar el SQL y **antes** de reemplazar el índice previo. `ContextIndex.refresh_notes` comprueba ese mismo inventario dentro de su transacción SQLite después de la proyección y antes de confirmar, y `refresh_existing_note` comprueba la versión física de la fuente antes de confirmar sus propiedades. Un cambio concurrente produce `ContextIndexError`: no se publica una proyección desactualizada, se conserva el índice anterior sin reparar silenciosamente datos personales. Los 3 caminos se han ensayado con un **proceso Python distinto** escribiendo el Markdown mientras corría el embedder, y además mediante intercalación determinista **después de preparar las filas SQL, justo antes de COMMIT/REPLACE**, en los tres mecanismos. Esas últimas tres pruebas comprueban expresamente el guard tardío y la reversión de la transacción. En reconstrucción completa y refresco incremental se verificó **igualdad byte a byte del fichero SQLite antiguo**, rechazo y recuperación mediante reconstrucción o reconciliación explícita válida.

El arranque opt-in `p4_indexes_reusable` vuelve a revisar el inventario fuente tras verificar también Context, Semantic y App indexes: editar la fuente a mitad del bootstrap hace que no reutilice los índices como frescos. Prueba con proceso externo y servicio semántico ya verificado. No afecta arranque tradicional DEV/PROD.

**Límite real que sigue abierto:** no existe transacción ni lock compartido con cualquier aplicación externa que edite Markdown; otro escritor puede actuar INMEDIATAMENTE después del último stat. Las evidencias de versión `(path,device,inode,size,mtime,ctime)` tampoco son firmas criptográficas frente a manipulación deliberada. Ningún índice SQL ni estas pruebas reemplazan el control CAS del Writer. Un `SELECT` negativo no concede autoridad absoluta; cualquier caso insuficientemente verificable debe abstenerse o acudir a la fuente.
