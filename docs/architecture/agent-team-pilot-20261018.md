## Política revisada de bloqueos para futuras rondas

Tras ejecutar los cuatro auditores sobre el código ChatGPT, se distinguieron dos fuentes de rechazo simultáneas: deficiencias reparables localmente frente a la falta de navegador autenticado/permiso/medición externa. `review.schema.json` exige que cada finding tipado clasifique `actionability=repairable|external`. El supervisor procesa errores reparables (o tests deterministas fallidos) y, si quedan intentos, reactiva Builder sin solicitar intervención al usuario, aunque otro auditor haya anotado un blocker externo. Si únicamente faltan evidencias externas, se detiene en `blocked_external_evidence` sin gastar más tokens; si se agotan las correcciones, `blocked_repair_budget`. CLI `run` devuelve exit 3 ante un bloqueo real; el estado JSON conserva la distinción entre fin de ejecución y aprobación. **21 tests de supervisor PASS; gate transversal 1077 Python + 174 JS PASS, siete subtests**, incluyendo doble bloqueo y segunda ronda, cuota de intentos y salida de shell. Esta política está testada de manera determinista, todavía NO validada con ejecución Builder Codex de escritura por falta de aislamiento Linux de la Raspberry.

## Optimización de cuota y selección automática de modelos (18-10-2026)

Tras el piloto de 249201 tokens reportados para una feature interna, se implantó la política declarativa `ops/agent-team/model-policy.json`: Luna `gpt-6-luna` esfuerzo low para cambios rutinarios, Sol `gpt-6-sol` medium para contratos Core/runtime/apps o riesgo declarado, Sol high para riesgo crítico y reparaciones arquitectónicas difíciles. Ambos modelos probados en la Raspberry con CLI 0.162.1 (`-m`, `model_reasoning_effort`), verificando el header de respuesta antes de aceptar el trabajo. No se utiliza un LLM adicional para escoger el modelo: la clasificación determinista combina rol, rutas de código cambiadas, riesgo declarado y número de iteración. Si el Builder va a modificar Core sin archivos cambiados todavía, marcar `--risk high` en la planificación; los revisores sí detectan el impacto real después. Sin garantía de que toda complejidad pueda inferirse automáticamente.

Cada job nuevo dispone de un límite por defecto **110000 tokens CLI reportados** (configurable `--token-budget`, entre 20000 y 300000). Cada sesión agrega un registro del modelo, tier, motivo y tokens al `status.json`, persiste el dictamen y bloquea antes de lanzar otro modelo si se ha superado el total. No equivale a un límite exacto dentro de UNA sesión ni a cuotas/precio de ChatGPT. El comando `route --job` previsualiza el coste de decisión sin gastar tokens. Las ejecuciones históricas previas al contador se muestran como no medidas (`null`) en lugar de fingir 0 tokens consumidos. El nuevo prompt de cada agente exige diff primero, documentos activos acotados y solo pytest focal; la suite transversal y el acceptance ledger se ejecutan UNA vez por ronda por el supervisor (evita repetir falsos fallos de socket en sandbox).

Se confirmaron en CLI real `gpt-6-luna` low y `gpt-6-sol` low; incluso la respuesta mínima `MODEL_OK` reportó 9278 y 8851 tokens respectivamente, señal de overhead de sesiones que no se elimina solo por escoger Luna. **54 pruebas focales del supervisor PASS; suite transversal 1110 Python +174 JS PASS, siete subtests** incluyendo selección de Sol por Core, escalada de reparación, gasto compartido, parser de uso, preview sin invocar IA, construcción real de parámetros CLI simulada y rechazo de sustitución silenciosa de modelo. Esta mejora está integrada en rama feature, sin deploy DEV/PROD. No se ha hecho aún prueba comparativa de los cinco agentes con modelos mixtos, y por tanto el ahorro real y la calidad equivalente siguen POR MEDIR.
