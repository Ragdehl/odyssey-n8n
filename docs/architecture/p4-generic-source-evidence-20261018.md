# P4 — Procedencia general de hechos sobre fuente inmutable (18-10-2026)

## Decisión y alcance

La procedencia original es un contrato **de Core y transversal a todos los tipos de Note/Apps**, no una solución para dos Tasks. Separar tres responsabilidades:

1. **Fuente literal original e inmutable:** `odyssey_core/source_provenance.py` recibe una cadena fuente y un `primary` más cero o más `supporting` fragmentos literales. Retorna offsets inmutables `SourceAnchor(start,end)` y `AnchoredEvidence`; cualquier subtipo futuro (Person, Project, Task, Calendar Day o App ficticia) puede usarlo sin código de casos. La ocurrencia debe ser única: texto modificado, paráfrasis, capitalización incorrecta o cita ambigua se **rechazan**; no seleccionar automáticamente la primera ocurrencia.
2. **Interpretación semántica independiente:** `PLAN_CORE_ANCHORED_SCHEMA` extiende el Planner con `source_evidence_fragments` (lista, vacía cuando no corresponda). El Reviewer `REVIEW_CORE_ANCHORED_SCHEMA` **no produce `source_quote`**, evalúa el original, todos los hechos del Planner, fechas, sujeto, negación, cardinalidad y referencias. Una fecha, predicado, sujeto o atributo original puede apoyar múltiples hechos, y cada hecho puede usar múltiples spans: N:M de evidencia; ningún número de hechos ni tipo de nota tiene lógica especial de procedencia.
3. **Autoridad canónica inalterada:** `validate_whole_message_coverage(...,core_anchored_evidence=True)` verifica las evidencias y el dictamen estructurado, preserva orden, dependencia, cardinalidad, identidades y rutas. El contrato revisado adjunta offsets como prueba técnica, **no** una autorización de WRITE. El compilador existente, SELF, E2/E3, el Writer Core y readback siguen obligatorios. Las wikilinks y Markdown añadidos luego no se comparan contra el texto literal de usuario: los autoriza Core contra el contexto verdadero.

Las nuevas estructuras están en la rama aislada y tras `WholeSourceLightExecutor.core_anchored_coverage_enabled` (por defecto `False`). El camino v1 permanece operativo sin cambios de comportamiento. **NO activado, integrado en composición DEV ni desplegado en PROD.** `task_create_batch_enabled` es otro flag existente independiente, no el dueño de la nueva lógica de procedencia.

- `scripts/odyssey_cross_surface_gate.py` incluye ambos conjuntos. Último gate: **1019 Python y 174 JavaScript PASS** (otros 7 subtests Python); incluye gráficos n8n/cliente/Source y E2/E3 anteriores. No demuestra navegador real.
- **GPT real sin escritura** en Raspberry con schemas y prompts V2 reales, tres mensajes sintéticos: 2 Tasks; 1 Core +3 Tasks enlazadas por fecha/predicado; 3 Core sobre 2 fechas. En cada caso, Planner y Reviewer devolvieron 2/2, 4/4, 3/3 hechos, `approved=true`, `complete=true`, todas las evidencias literales correctamente ancladas, cero citas autoritativas regeneradas.
- **GPT real + runtime + Writer físico en vault efímero**: dos obligaciones previamente bloqueadas por `Atomic source evidence mismatch` -> `completed` (18,77 s), 2 Task Notes + 2 recibos, replay con mismo delivery ID `delivery_replayed=true`, Markdown idéntico. El _fixture aislado no aporta todos los adaptadores de grafo N:dependientes, así que rechaza antes del Planner/Reviewer V2. No atribuir ese bloqueo al contrato nuevo ni afirmar que cuatro operaciones funcionan E2E en DEV: necesitan recorrido integrado completo.
- Suite Python completa: **3958 PASS / 80 SKIP / nueve FAIL históricos** (benchmarks de costes y hashes de contratos antiguos, exactamente el conjunto previo), otros 52 subtests PASS; ningún nuevo fallo atribuible al contrato v2.

## Riesgos abiertos y próximos gates

- Probar más variación GPT incluyendo mezclas Core/Task/WorkSession, frases multilingües, referencias elípticas y negación; los checks de estructura no garantizan comprensión semántica.
- El anclaje actual exige ocurrencia única. En fuentes que repiten literalmente `mañana`, una persona o una cláusula, falla cerrado. Antes de adopción general debe decidirse una forma **tipada y validada de desambiguar ocurrencias**, nunca hacer matching aproximado ni seleccionar heurísticamente la más cercana.
- Las 16 entradas por mensaje y hasta 16 soportes son límites técnicos del contrato, no reglas semánticas por número de Tasks/Notes. Revisar presupuestos y degradación explícita para mensajes mayores.
- Modelo aislado de 4 hechos sí pasó Planner/Reviewer, pero producto integrado N:M con aristas Core→Task y Task independientes queda bloqueado en fixture por falta de adaptadores; requiere prueba completa con adapters productivos en DEV y prewrite compartido sin perder ninguna operación.
- Verificar nueva variante ante el gate real navegador autenticado→n8n→GPT→Core Writer→Markdown/graph/donut y readback tras recarga, indexación, SELF y replay de E3. Cloudflare `/api/presence.js` sigue ausente de inventario público DEV y su actualización necesita autorización separada.
- No activar solo por resultados felices: validación adversarial y original fuente completa deben continuar protegiendo contra omisiones. No PROD, merge, push ni datos personales.
