# P4 — lote de tareas CREATE por el compilador y Writer canónicos (18-10-2026)

## Motivación y frontera

El mensaje de dos obligaciones «tengo que llamar al electricista y revisar la factura» fue rechazado por un auditor de Task-only: only_task_semantics=false, exactly_one_operation=false. La ruta existente tenía como precondición una sola operación; delegar arbitrariamente la primera tarea descartaría contenido del mensaje y sería inseguro. El compilador Core whole_source_compiler ya soporta múltiples Task CREATE revisadas, y TaskLifecycleGuard valida cada escritura con el mismo mecanismo E3/Markdown.

## Cambios de rama, opt-in DEV

- La auditoría independiente separa dos dimensiones: only_task_semantics significa que TODO el mensaje pertenece a Tasks (puede incluir varias acciones); exactly_one_operation determina su cardinalidad. Mensajes mixtos con un hecho Core mantienen only_task_semantics=false. La ruta de un solo comando Tasks permanece intacta y conserva interpretación, lifecycle y WorkSession service.
- Si la auditoría prueba todas-las-tareas y más-de-una-operación, y solo con task_create_batch_enabled (flag DEV), el coordinador usa la ruta habitual del Planner de mensaje completo, el auditor independiente mixed_task_create y los revisores coverage + speaker A/B. Se exigen al menos dos facts de kind=task (no convertir dos obligaciones en una). Los comandos de lifecycle o WorkSession no pasan el auditor de solo Task CREATE y se rechazan.
- El mismo compile_reviewed_operations de Core compila TODO el lote antes de una sola escritura. Cada RequestPlan se envía a execute_request con TaskLifecycleGuard(TaskOperation.CREATE), mismo Writer, readback, E3 idempotencia y eventual indexación que en cualquier otra ruta. No hay alternativa de escritura en la aplicación Tasks.
- Limitación deliberada del compilador existente: para crear Tasks a través de este seam cada revisión necesita una fecha de destino explícita que se pueda probar; un lote sin fecha sigue rechazándose, en lugar de inventar fechas/propiedades. El soporte general de Tasks sin fecha deberá hacerse como ampliación de contrato, no con una fecha ficticia.

## Diagnóstico causal sin mutaciones (18-10-2026)

**Fuentes:** llamadas nuevas al GPT real mediante `WholeSourceLightExecutor._ask` en ejecución aislada, usando exactamente `PLANNER_INSTRUCTIONS/PLAN_SCHEMA`, `PROMPT_SOURCE_REVIEW/REVIEW_SCHEMA` y `validate_whole_message_coverage`, con tres mensajes sintéticos y notas/veredictos inspeccionados en memoria. Solo diagnóstico de dos etapas: no es un E2E ni autoriza corregir seguridad basándose en tres muestras.

1. `failure_a`: Planner devolvió dos Tasks, la segunda con `source_evidence="tengo que enviar una caja de prueba y revisar un recibo de prueba"`. Reviewer `approved=true`, `complete=true`, dos filas, y para la segunda `source_quote="revisar un recibo de prueba"`. Ambos spans aparecen exactamente en la fuente; ordinal/kind/date/supported/clarification coinciden. Sin embargo `requested not in quote` es verdadero. Motivo preciso del rechazo: comparación de **inclusión direccional entre spans literales válidos** cuando la propuesta usa un span común a dos hechos. El revisor usa un subspan legítimo.
2. `failure_b`: Planner para el segundo Task `source_evidence="llamar al mecánico de prueba"`; Reviewer usa `source_quote="recuérdame llamar al mecánico de prueba"` aunque en el original se dice `recuérdame entregar ... y llamar ...`. El reviewer generó una frase equivalente pero **no contigua**, de modo que `quote not in source` es verdadero. Esta validación protege la procedencia y NO debe suprimirse.
3. `success`: Planner y Reviewer produjeron citas literales compatibles para dos recordatorios, y el mismo validador aceptó la revisión. En las tres muestras el reviewer se consideró completo, con dos filas y fechas/clases de Task iguales a la propuesta; los rechazos se explican por condiciones literales distintas bajo el mismo error general `Atomic source evidence mismatch` (código 11).

**Diagnóstico arquitectónico:** `source_evidence` es una propuesta semántica (puede contener predicado/imperativo compartido con varias acciones), mientras Reviewer construye libremente otra cadena `source_quote`. El Core actual impone `requested in quote` Y `quote in source`, además de orden/cardinalidad/fechas. Aunque no contiene reglas por «caja», «mecánico», fecha o Task, mezcla la comparación de spans con la corrección semántica. El texto del prompt pide citas literales pero además pide reformular Tasks como etiqueta accionable en `reviewed_text`; ocasionalmente el modelo aplica esa reformulación también a `source_quote`.

**Dirección de reparación genérica (sin implementar aquí):** Core/compiler debe poseer los spans exactos/offsets del original y su trazabilidad; la revisión semántica independiente debe evaluar el significado y la correspondencia N:M, pero no generar un segundo texto literal independiente como autoridad. Conservar prueba de ocurrencia única o desambiguación por offsets, orden, identidades, negativas, dependencias y cardinalidad, y vetar toda cita no existente. Una simple condición `requested in quote OR quote in requested` no resuelve el caso de la cita parafraseada y podría permitir cobertura demasiado amplia; un reintento GPT sin guard no prueba corrección. Añadir regresiones abstractas de coordinación con imperativo compartido, subspans, paráfrasis falsas, hechos omitidos, casos Core+Tasks, sujeto elíptico, negación, dates y repeticiones; validar físico en aislado, luego GPT + DEV antes de abrir pruebas manuales.
