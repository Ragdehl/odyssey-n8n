## Causa demostrada en segundo E2E real (`54ca18b` en DEV)

Solicitud `p4dev20261017-localtiming02`, fuente sintética: «El 12 de octubre de 2026 ordené una libreta de prueba y el 13 de octubre de 2026 limpié una caja de prueba». **75,1 s cliente**, runtime **73,931 s**, Core P4 **68,818 s**, `completed`, dos Day Markdown y links SELF, 2 mutaciones Core 251+221 ms. En la traza nueva:

- GPT Router 3,614 s; Planner 2,837 s; cobertura 2,866 s; speakers 1,680/1,859 s en paralelo: hasta el fin de los modelos **~11,33 s**.
- `local.synchronous_index_refresh` tras el primer hecho **26,749 s**; tras el segundo **30,111 s**; total **56,860 s = 76,9% del runtime**. El contrato productivo `RuntimeComposition.execute_product` ya dispone de `DerivedIndexRefreshCoordinator.schedule()` después del resultado y `wait_until_clean()` antes de las lecturas indexadas; estas dos llamadas internas **duplicaban** trabajo y bloqueaban la respuesta.
- Otros pasos: source hints 1 ms, identity collision <1 ms, compilación <1 ms, snapshots 16/7 ms, Markdown readback 62 ms. Por tanto, **no culpar a GPT, búsqueda o Writer del sobrecoste**.
- El recibo HTTP nuevo sí contenía `request_detail.flow` con una ruta Core verídica y `writes` para ambas fechas, más `execution_ledger` transitorio. El transcript **no** conservó `request_detail`: `_validate_request_detail` permite `flow` pero rechaza el campo adicional `execution_ledger`, y el persistidor hace fallback a texto. Reproducido contra validador real: detalle íntegro FAIL, sin `execution_ledger` PASS. El navegador real mostró el nuevo mensaje tras recarga pero sin botón `ⓘ`; el botón antiguo seguía abriendo solo el gráfico antiguo sin `flow`. No afirmar éxito de la nueva UI hasta probar un turno nuevo.

**Corrección en rama después del diagnóstico**: `WholeSourceLightExecutor` deja de refrescar derivados entre operaciones Core previamente revisadas y compiladas; la frontera productiva programa UNA actualización final con todos los IDs reales, y el siguiente lector de índices espera el barrier existente. `assert_reviewed_markdown` sigue probando los links origen→destino con las `body_blocks` resueltas del Markdown actual (el inverso es backlink físico), sin consultar una tabla de backlinks que inevitablemente estaría pendiente de actualizar. La integridad posterior de `NotesQueryService.backlinks` se verifica tras completar la actualización. El persistidor elimina **solo** `execution_ledger` temporal de la copia que almacena; mantiene el esquema estricto de `flow`, `stage_view` y resto, y rechaza los demás campos desconocidos. Tests con Writer físico, dos fechas, único refresco y grafo/SELF; tests HTTP de persistencia de flow pese al ledger. No cambiar PROD.
