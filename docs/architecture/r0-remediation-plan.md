## Objetivo irrenunciable

**No se permite lógica semántica específica para NINGUNA forma de entrada: ni tipo de nota, clase de frase/intención, orden de palabras/oraciones, posición o secuencia de fechas y referencias temporales, combinaciones de tipos, idioma, sujeto, parentesco, propiedad, cantidad o ejemplo concreto.** El significado se interpreta con la fuente completa y el contexto; los contratos tipados y las comprobaciones generales de evidencia/autorización deciden, no una tabla de casos. Las reglas declaradas del ciclo de vida de cada App y las verificaciones de esquema/seguridad siguen siendo legítimas, nunca excusas para un segundo enrutador semántico. **No más orquestadores semánticos alternativos.** El mensaje y su contexto E2 viajan completos por los puertos existentes; la IA interpreta cualquier formulación y puede abstenerse; Core valida origen, identidad, evidencia, relaciones, propietario y escritura canónica; Tasks y Events deciden solo su propio ciclo de vida; Runtime conecta etapas, dependencias y recibos sin reinterpretar su contenido. Cada afirmación/acción justificada llega a su nota/App correcta (N:M entre frases y hechos), incluso para tipos de nota creados por el usuario. Evidencia ambigua → no inventar; falta de interpretación → error explicable. **Conservar** actor/autorización, frontera E3, revisores independientes, lectura física, crash/replay y completitud original.

**No repetir E3:** E3 Writer/Core planificador/ExecutionContext/ApplicationCatalog ya existen; se reutilizan. Se retira código solo tras comprobar que se ha sustituido, no por su tamaño. Ninguna corrección de un ejemplo puede añadir un `if` específico de ese ejemplo.

## Procedimiento para cada hallazgo — evita volver a empezar de cero

1. **Localizar en la fuente activa** (`git`/flags/llamadas reales) la restricción y el **mecanismo genérico existente** que ya realiza su trabajo. Revisar antes la evidencia inmutable del hallazgo, el estado del registro y los tests previos. No volver a programar una responsabilidad ya cubierta.
2. **Test de ruptura antes de modificar**: reproducir el rechazo o la ruta duplicada con notas sintéticas. Probar también una frase equivalente de otra forma, otros tipos de nota, varios hechos, relación ambigua y ausencia de evidencia; ninguna prueba basta si solo hace `needs_attention` donde debía escribir/responder.
3. **Cambio mínimo y consolidación**, nunca un parche por frase, tipo de nota, posición temporal, orden de oraciones ni combinación de rasgos. Cada corrección explicita `mecanismo existente → defecto general → propietario reutilizado → código redundante retirado (o retirada pendiente justificada) → pruebas positivas y negativas del resultado final con distintos tipos y permutaciones`. Mantener source exacto, autenticación, límites de recursos legítimos, revisión semántica independiente y Core/E3 como autoridad. Si se retira un camino, aportar el inventario de consumidores, flags y pruebas equivalentes. Un plan que altere la seguridad, NoteSchema o decisiones humanas requiere revisión del usuario antes de implementarse.
4. **Pruebas y resultado final**: Py/JS focales + gate transversal; cuando se toque la semántica, prueba navegador/n8n/modelo real sobre bóveda desechable y SHA coincidente, con Markdown/UI/replay. Registrar el antes→después, rutas afectadas, tests y errores nuevos. Un test local no equivale a R0 aceptada.
5. **Cierre trazable**: pasar `open → in_progress → code_verified → closed` únicamente con commit, evidencia de antes/después, tests verificables e informe de auditor independiente. `code_verified` significa código probado, **no** GPT+navegador. No marcar `closed` sin la revisión de cierre del hallazgo; el gate R0 completo sigue siendo independiente y obligatorio. Si una advertencia se decide legítimamente no aplicable, justificar la ruta inactiva o la frontera de seguridad con pruebas, no borrarla del registro. Cada intervención actualiza su grupo y sus hallazgos. Cada error nuevo del usuario se registra **sin modificar los 24 orígenes** en `followups` (IDs `R0-N001` en adelante), con mensaje de prueba anonimizado, efecto esperado, resultado real y grupo responsable; se añade asimismo a las regresiones de aceptación pertinentes. Nunca se resuelve con un `if` para esa frase.
