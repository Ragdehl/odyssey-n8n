# P4 — Core → Task dependiente en composición productiva (17-10-2026)

**Estado:** implementado en rama experimental, **NO AUTORIZADO PARA DEV/PROD**. Fuente de estado: `functional-roadmap.md`. Este documento explica qué rutas concretas están probadas y cuáles aún no. No confundir una batería congelada E2E local con n8n/navegador/LLM real.

## Contrato de referencia, propiedad y operaciones

Una petición de usuario puede escribir un hecho personal y, en la misma fuente original, pedir una operación sobre una Task **ya existente mencionada en ese hecho**. El Router P4 es solo un selector de capacidades; `interpretation=joint` y algún `app_scope.depends_on_another_scope=true` activan el candidato dependiente exclusivamente cuando la aplicación Tasks está habilitada. Las rutas Core, Tasks-only e independientes anteriores siguen en los mismos servicios. Una obligación nueva con antecedente de persona (por ejemplo Maite y «tengo que llamarla») sigue su ruta probada de **Core+Task CREATE ordinaria**; no se convierte en una Work Session, ni usa un `task_id` derivado de persona.

1. **Antes de cualquier escritura**, modelo `DEPENDENT_TASK_PARTITION` propone dos *spans byte exactos*: antecedente Core y ámbito Tasks. `odyssey_core/dependent_source_scopes.py` valida que cubran **todos** los caracteres originales, sean contiguos, con una única mención dependiente exacta, sin sustitución de nombres o campos de identidad.
2. El **intérprete Tasks productivo** identifica la operación y su fuente exacta; si necesita una hora, **Temporal productivo la resuelve antes del primer WRITE**, usando la fecha/hora `datetime` capturada al entrar el mensaje. Si no hay hora exacta, el rol temporal no coincide o el proveedor falla, no se escribe nada. Luego el auditor genérico `TASK_ONLY_SCOPE` debe acreditar que el segmento Tasks contiene exactamente una operación, sin fact independiente o segunda operación omitida.
3. Dos revisores semánticos de P4 con modelo y prompt distintos corroboran fuente/antecedente/mención/tipo `task`, **la misma operación solicitada**, con estricta salida JSON sin IDs. `verify_dependent_task_semantics()` examina las dos respuestas ANTES de escritura. El Router, los dos revisores y el intérprete no otorgan permiso para usar Note IDs.
4. **Core general (`core_execute`)**, no el compilador ligero P4, planifica y ejecuta el hecho previo con Writer y `execute_request` habituales. Esto es importante: el compilador ligero actual tiene referencias tipadas exclusivamente como `person`; no se lo ha parcheado por frase o ID. Core debe persistir un enlace físico a **una** Task existente y devolver el `CanonicalReferenceEvidence` correspondiente a ese hecho nuevo. Si el resultado no es COMPLETED se detiene; si escribió el hecho pero no acreditó Task, el resultado global es **PARTIAL**, sin operación Tasks.
5. `prove_dependent_task_target()` y `_dependent_evidence_is_current()` vuelven a comprobar **Markdown actual del hecho y de la Task**, y que la prueba derive de la misma acción Core terminada. La prueba es válida solo si está vinculada a una Task y no a una persona, alias dudoso o una nota modificada. No se resuelve el pronombre mediante una búsqueda libre o creando Note.
6. `execute_tasks(..., dependent_task_target=...)` reutiliza el caso de uso productivo y el mismo **`TaskWorkSessionService`** de Notes/UI. Revalida la evidencia justo antes de la mutación; START exige revisión y hash actuales (CAS) mediante `task_mutation_tokens` read-only del servicio. STOP, EDIT y ADD_WORK_SESSION_ACTIVITY usan sus métodos normales de dominio y protección de concurrencia. **No hay nuevo Writer, mutación directa de Markdown, caché de permisos ni reintento ciego**.
7. `RuntimeComposition` conserva **un único claim E3 exterior** que cubre ambas escrituras. Mismo ID+fuente reproduce el recibo inmutable, diferente fuente con mismo ID da conflicto, una caída simulada tras escribir bloquea el reintento. La ruta devuelve una proyección `execution_flow` Core+Tasks (sin inventar resultados), stages de progreso observados y los IDs de notas realmente afectadas. El índice incremental se **programa solo una vez al final del delivery**; no hay segundo escaneo/embedding entre Core y Tasks, porque la referencia se verifica en Markdown.

## Evidencia local en fixture aislado

- `tests/core/test_p4_dependent_source_scopes.py`: 18 validaciones sin patrones de frases, incluidos bytes perdidos, fuente reordenada, span dependiente duplicado, ID añadido, casos ES/FR/EN.
- `tests/runtime/test_p4_dependent_router_integrated.py`: ruta P4 Router joint → spans → Task interpreter + auditoría Tasks-only → dos revisores → `execute_request` Core real con enlace Task → `TaskWorkSessionService` → E3; negativa de fuente/revisor/operación/tipo Task, sin escrituras; prueba distinta de no enlace Core que conserva PARTIAL; Task CREATE normal no cambia de semántica; subtarea sin título Planner queda rechazada antes de WRITE; interrupción después de los dos WRITE deja claim E3 y cero duplicados en retry; negativos de Temporal prewrite (proveedor caído, evidencia ausente, fragmento cambiado) con cero escrituras.
- `tests/runtime/test_p4_dependent_factory_product.py`: **`build_runtime_from_environment()` real** (`ODYSSEY_LIGHT_SOURCE_V1=1`, Tasks habilitado) con directorios desechables y SELF auténtico, índices verdaderos pero embeddings deterministas, Planner y respuestas de IA congelados. Reproduce **cuatro entregas** independientes Core+Tasks sobre la misma Task: START, ADD_WORK_SESSION_ACTIVITY, STOP y EDIT de Work Session con hora explícita. Cada antecedente es un hecho nuevo y físicamente enlazado; Core no inventa evidencia para un hecho idéntico ya guardado. Comprueba exactamente una Work Session canónica con actividad y horas correctas, Notes UI leyendo/escribiendo su mismo estado, E3 replay de todas las entregas, e **inmutabilidad** del Markdown tras cada retry. Incluye HTTP TCP local (`POST /execute`, `/notes`, `/conversation/progress`) con actor autenticado y JSON UTF-8, flujo Core+Tasks y estado para donut; **no** navegador ni n8n reales.
- **Cruce de medianoche**: prueba con reloj del servidor ya en 17-10 pero `delivery_instant` inmutable en 16-10; Core Planner, Work Session y Temporal trabajan con la fecha capturada. **Rendimiento**: se verifica una única programación de refresh de IDs combinados por cada entrega Chat (en vez de indexar después de cada operación). La mutación UI independiente conserva su propio mecanismo de actualización, sin contador de chat duplicado. El objetivo sigue siendo perfilar a escala 250/1000/5000 Notes en Raspberry.
- **Opt-in**: factory de P4 con `ODYSSEY_ENABLED_APPLICATIONS` sin Tasks deja deshabilitados todos los adaptadores de referencia Task dependiente, aunque P4 esté activo.

## Límites y próximos bloqueos reales

- **Modelos:** las baterías nuevas han congelado el Router, dos revisores, Task/Temporal y Planner, para hacer reproducible la verificación de arquitectura. El circuito nuevo **aún NO ha superado pruebas de variabilidad con GPT fresco**. No se puede inferir disponibilidad lingüística de pronombres, ni desempeño, costes o tasa de éxito a partir de los fixtures.
- **Subtareas:** existe en `odyssey_apps.tasks.dependent_target` el contrato de parent Task y un test real `TaskDirectMutationService.create_subtask` con título explícito. **El Router dependiente P4 todavía bloquea la subtarea antes del primer WRITE con `DEPENDENT_SUBTASK_PLANNER_NOT_READY`**, porque falta derivar título/intención con el Planner Core ordinario sin perder ni inventar hechos; no se ha conectado una ruta directa artesanal.
- **Complejidad:** esta versión cubre **un** antecedente Core y **una** operación dependiente Tasks con **una única** Task canónica recién enlazada. No cubre N:M grupos/targets, edición de Task genérica dependiente ni selecciones conversacionales entre turnos sin prueba adicional.
- **E3 crash:** la seguridad está probada (claim incierto retenido, no duplicación) pero la **reconciliación automática post-WRITE sin recibo** sigue pendiente; no borrar claims para mejorar tasa de éxito.
- **Adopción:** falta secuencia auténtica **navegador autenticado → n8n real → GPT fresco → Core/Tasks → Markdown físico → gráfico/donut/historial en navegador**, más profiling CPU/RAM e índices de Raspberry y evaluación del coste de la nueva batería semántica. NO desplegar P4 todavía; DEV permanece `1474681` en el cierre de esta ronda, PROD/notas personales intactos.
