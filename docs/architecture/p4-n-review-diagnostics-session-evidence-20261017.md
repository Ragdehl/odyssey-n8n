# P4 — Motivos cerrados de auditoría N:M y evidencia física de sesión (17-10-2026)

## Auditoría semántica (sin rebajar el fail-closed)

El revisor de fuente N:M devuelve ahora los campos estrictos `review_reason` (enum APPROVED, SOURCE_COVERAGE, GROUP_CLASSIFICATION, GROUP_ATOMICITY, DEPENDENCY_AMBIGUOUS, DEPENDENCY_UNGROUNDED, DEPENDENCY_MISSING, OTHER) y `failing_group_index` (entero del grupo propuesto o null). No transmite razonamientos, IDs, notas ni instrucciones de escritura. Una aprobación **requiere** todos los campos habituales, source literal completo, grupos idénticos, flags `complete=true`/`dependency_edges_verified=true`, reason APPROVED e índice null. Los códigos rechazados nunca pueden autorizar la operación. El validador `classify_dependent_group_review_rejection` admite **únicamente** respuestas vetadas, con `groups=[]`, reason no aprobado, índice válido y sin campos adicionales; el runtime devuelve una clave acotada `DEPENDENT_N_GRAPH_REVIEW_<reason>` para diagnóstico y congela el E3 receipt sin Markdown escrito. Una respuesta inconsistente o una identidad no autorizada sigue generando el rechazo genérico anterior.

**GPT aislado real (solo fuente sintética, sin usuario ni DEV):** se ejecutaron dos ensayos tras introducir este enum con dos llamadas por ensayo y credenciales protegidas. El primero usó la frase de inicio «Ahora empieza una sesión…» tras dos hechos pasados sobre Tasks; la propuesta era Core/Core/Tasks con 3 grupos y arista 0→2, pero la auditoría rechazó con `GROUP_CLASSIFICATION`, índice 2. Se volvió a intentar **una vez** con la orden explícita «Por favor, inicia ahora una sesión…»: el proponente volvió a entregar Core/Core/Tasks, el auditor vetó con `OTHER`, índice 2. **0/2 nuevos grafos aceptados.** No se interpretan esos códigos de origen LLM como explicación causal verificada ni se ha suavizado el gate. El diagnóstico mejora visibilidad, no alcanza estabilidad en vivo; queda pendiente examinar por qué una orden explícita no obtiene revisión consistente, y comprobar varias familias gramaticales sin hacer ajustes por frase.

Pruebas: `tests/core/test_p4_dependent_group_graph.py` comprueba rechazo enum, índices, fuente, extras/IDs y que todo veto falla cerrado. `tests/runtime/test_p4_dependent_n_graph_execution.py` demuestra que cuatro razones concretas producen needs_attention y replay idéntico con **CERO escrituras**, Work Sessions o manifests.

## Portador canónico de Work Session (E2, NO conectado todavía a ejecución Task→Task)

Nuevo módulo de propiedad exclusiva de la app Tasks `odyssey_apps/tasks/session_evidence.py`. `prove_created_session` acepta SOLO un `WorkSessionMutationResult` *recibido de un `TaskWorkSessionService.start()`* en el recorrido autenticado de una petición, comprueba `operation=work_session_started`, ausencia de revision previa y coincidencia Task, path, ID, revision y hash SHA-256 de la Work Session canónica materializada, estado ACTIVE, y unicidad de ID de Task y sesión. Registra también hash físico del Task padre y el root del vault actor-local. Devuelve una `CanonicalSessionEvidence` privada, sin método de escribir y sin exponerse en JSON, modelo ni índices. `require_current` verifica de nuevo ambas Notes, hashes, IDs, ownership, ruta, estado y root; deja de ser válida después de STOP, edición/borrado, cambio del Task o duplicación de identidad. Para actuar se siguen usando los métodos **existentes** de WorkSessionService, pasando sus CAS (revision/hash) y su puerta canónica E3, jamás una segunda implementación de Writer.

`tests/apps/tasks/test_session_evidence.py` usa Markdown físico y `TaskWorkSessionService` real: START→evidencia→STOP por servicio existente, caducidad tras STOP, recibos adulterados, ID/path/tarea erróneos, Note externa modificada/soft-deleted/reowned, IDs duplicados, Task cambiado y root actor distinto, incluso con el mismo Markdown copiado. La evidencia **no demuestra** por sí misma que un pronombre refiere a una sesión ni qué grupo Tasks produjo el recibo: falta un handoff tipado y revisado de `Task→WorkSession` dentro del DAG y una prueba de completitud E3 para permitir START→STOP/ACTIVITY compuesto. Por eso `validate_task_batch_prewrite` sigue vetando la cadena START→STOP en un único mensaje antes del primer WRITE.
