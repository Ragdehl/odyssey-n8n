# C3 — Chat, ayuda y continuidad segura (23-10-2026)

**Estado (segunda entrega de integración):** el código ya enlaza C1–C3 con `RuntimeComposition.execute_product` y la proyección existente de `workflows/odyssey-online.ts`, **solo como opción `ODYSSEY_CHAT_C3_ENABLED=1` en DEV; desactivada por defecto y NO desplegada**. Sin nuevos endpoints públicos, writer, historial ni permisos. Todavía no se ha aceptado con n8n/DEV real. No se han modificado Core/E3, vault personal ni PROD.

## Resultado y límites

- `odyssey_runtime/conversation_chat.py` reutiliza `OpenAIConversationGateway._complete`: una salida estricta con `outcome`, `answer`, `supporting_ids`; sin herramientas, plan, escritores, reintentos ni permiso de escritura.
- La clasificación de entrada C1/C2 es anterior e independiente. Solo después de recibir `CHAT` sin decisiones canónicas pendientes, un segundo modelo barato puede etiquetar `HELP` o `GENERAL`. `ROUTER` se conserva íntegro (texto original, sin parafrasear), y una referencia conversacional pasada por `CONTEXT` puede recibir `PRIOR_CONVERSATION` con fuentes verificables.
- `dispatch_before_chat` inspecciona el `LocalClarificationStore` y `CandidatePendingRepository` existentes ya vinculados al actor; si queda alguna decisión Core pendiente, conserva la ruta de continuación de Core. No intenta resolver opciones ni reescribir el pedido original. Estado corrupto: falla cerrado. Una validación final y el consumo/almacenamiento corresponden a la ruta Core original.
- `load_verified_help` lee la ayuda versionada **solo** para un conjunto inyectado por el servidor de capacidades realmente desplegadas. No acepta contenido arbitrario ni una ruta externa. La rama `GENERAL` recibe cero párrafos de ayuda; la rama `HELP` recibe únicamente secciones aceptadas. El adaptador de composición selecciona únicamente funciones instaladas (`Notes`, Tasks/Work Sessions y Calendar), no una lista suministrada por el navegador o la IA. Su correspondencia con el DEV finalmente desplegado aún debe comprobarse allí.
- `PRIOR_CONVERSATION` usa hasta 8 turnos ya recuperados del almacén actor-bound, máximo 4096 bytes; citar IDs de turnos no certifica una identidad para Core. Preguntas de conocimientos personales guardados se siguen enviando al Router y su answerer fundamentado actual de n8n, no al Chat social.
- Respuestas `ChatReply.product_response` son compatibles con el endpoint existente `/conversation/assistant-response` y su protocolo de respuesta, sin un segundo historial ni una escritura directa desde C3. Una prueba HTTP sintética verifica persistencia, no duplicación y rechazo entre actores.

## Pendiente para aceptar y activar C3 en DEV

1. Revisión independiente del cambio de integración y una matriz fresca más amplia con Luna real, incluyendo conversaciones repetidas, mensajes mixtos de Chat y guardado, referencias inciertas, aclaraciones intercaladas y errores de transporte. Registrar falsos positivos que podrían suprimir escrituras antes de activar el clasificador.
2. Comprobar que la versión de DEV instala efectivamente las capacidades que anuncia el adaptador interno; mantener `ODYSSEY_CHAT_C3_ENABLED` desactivado fuera de un ensayo autorizado y aislado. Obtener autorización de despliegue, preparar copia de seguridad y rollback, desplegar un SHA completo fijado y verificar coherencia de runtime/n8n/marker.
3. Ejecutar la aceptación **como usuario desde el navegador autenticado de Odyssey DEV** con n8n y GPT reales, con datos sintéticos. Escribir/consultar/guardar, continuar aclaraciones, recargar, navegar Notes y Calendar y contrastar capturas/DOM, traza e identidad con Markdown físico y recibos E3. Confirmar que el Chat puro no guarda notas y que el guardado sí llega a Core.
4. Si falta cualquier tramo real navegador → n8n → GPT → Core/E3 → Markdown → UI, registrar `APP E2E NOT VERIFIED` y no declarar aceptada la funcionalidad. Ninguna prueba sintética autoriza PROD.

**Decisión arquitectónica:** PROCEED solo en incremento read-only. La ruta de persistencia de conversación y la continuación Core ya existen; crear un motor de chat paralelo, un historial nuevo o un escritor duplicado añadiría riesgo sin beneficio. La etiqueta de ayuda añade una llamada breve únicamente después de `CHAT`, y su coste/latencia deberá medirse en una integración real antes de adoptarla.
