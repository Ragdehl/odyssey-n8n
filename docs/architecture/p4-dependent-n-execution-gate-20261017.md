# P4 — Primer coordinador N dependiente y veto de sesiones sin evidencia E2 (17-10-2026)

## Alcance introducido, rama `feat/light-router-poc-20261016` exclusivamente

`WholeSourceLightExecutor._execute_dependent_graph` conecta la ruta `joint` de **3 o más** ámbitos con el contrato `verify_dependent_group_graph` y `prove_canonical_group_handoff` que ya existían. Usa exactamente los mecanismos habituales: Router como sugerencia, partición literal completa + auditor independiente, Tasks Interpreter/Temporal, dos revisores semánticos del objetivo por cada grupo Tasks, Planner/Writer Core existente, WorkSession/TaskDirectMutationService de Tasks y claim/recibo E3 exterior. No genera nuevos IDs canónicos desde Router. Preserva el orden completo de grupos y los links hacia el antecedente real en `execution_flow`, sin convertir la descripción de grupos en hechos.

La preparación de **todos los grupos Tasks** (interpretación tipada, Temporal, auditor de `exactly_one_operation`, revisores A/B, título de subtarea si procede) ocurre **antes de cualquier WRITE**. Las aristas se corroboran nuevamente a posteriori con el backlink Core y los hashes actuales de source y target; el servicio Tasks vuelve a validar CAS. Antes de un segundo Core se refrescan únicamente los IDs afectados, sin reconstrucción de índices como escape; un fallo tras otro WRITE devuelve `partial` veraz y recibo E3 durable. El manifiesto E3 registra TODOS los grupos antes del primero WRITE, los resultados observados por orden y deja un claim irresuelto en crash postwrite, nunca reintenta a ciegas.

**Límites deliberados:** en esta primera ejecución N, los grupos Core NO pueden depender de otros grupos; cada grupo Tasks exige exactamente **un** objetivo de Task con un enlace proveniente de un grupo Core. Un grupo Task con varios padres/targets, una dependencia Task→Task, una dependencia Core→Core o una capacidad fuera de Core/Tasks provoca `needs_attention` ANTES de cualquier WRITE. Las mutaciones con dos sesiones activas y una secuencia START→STOP creada en el mismo mensaje se vetan a nivel Tasks: un enlace a la Task NO prueba cuál es la Work Session concreta; hace falta una `CanonicalSessionEvidence` tipada y con lectura física que **aún no existe**. El validador de dominio `validate_task_batch_prewrite` detecta esas secuencias antes de escribir Core, sin sustituir las reglas de WorkSessionService.
