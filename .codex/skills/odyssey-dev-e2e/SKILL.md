# Odyssey DEV E2E and safe adoption

1. Run `odyssey-start-work` and context doctor. Distinguish working source SHA, immutable target commit, DEV checkout, `/data/odyssey-dev/runtime/deployed-commit`, runtime/n8n HTTP, Git remote and PROD. Detect another deployment/job **before** mutation.
2. Evidence pyramid: focused tests → `python scripts/odyssey_cross_surface_gate.py`, acceptance ledger, Ruff → isolated real-provider E2E if model-facing → **authenticated, user-driven Chromium/browser journey through the real Odyssey app** → Markdown + UI readback. Do not equate Python green, browser-only fake provider and real GPT E2E. **App-level user testing is mandatory before claiming a user-visible feature accepted; it is not optional after a green suite.**
3. Cover relevant actions: create/update/query/cancel Events; Tasks/subtasks/Work Sessions; calendar month/day/1/3/7 views; Notes/backlinks; route diagram, donut, stage timings; idempotence, stale/ambiguous refusal and reload persistence.
4. DEV writes use synthetic names/data with bounded authorization. PROD/private vault is out of scope. Before deploying a clean **pinned full SHA**, retain verified backups and last-good rollback; use tracked `scripts/odyssey-dev` and `docs/architecture/phase-21-development-isolation.md`. Do not race or interrupt n8n import or run overlapping deployments.
5. If import/readback fails, separate n8n startup, runtime, provider semantics, E3 writer, UI and timing/checkout races. A test running during another deploy is inconclusive. Recover the last complete known-good DEV state; verify matching marker, checkout, services and vault.
6. Document exact tested SHA, actual deployed marker, tests and authenticated browser evidence, backups, limitations and errors. Never claim universal regression-free behavior.

## Mandatory real-user app acceptance (every user-facing feature)

- Open the **actual deployed Odyssey DEV app** in Chromium with a legitimate test-user session. Interact via the visible UI **as an ordinary user**: type messages in Chat, submit, click buttons, select clarification options, navigate Notes/Calendar and refresh/reopen. Never substitute a direct Python function, HTTP request, n8n node execution, simulated response or DOM injection for the user journey. These can be complementary diagnostic tests only.
- Exercise several realistic, **synthetic** end-to-end conversations, not just a happy-path smoke test: straightforward save, read/query, contextual follow-up, correction or cancellation, ambiguous identity/clarification, mixed chat + save, and repeated request/reload. Adapt the matrix to the feature; for Chat C1–C5 verify social reply, Odyssey-help reply, previous-chat context, safe abstention/error and routing to Core for writes.
- Verify the complete path **from user-visible action to observed result**: browser → authenticated n8n → actual provider/model where required → Router/Core/E3 → physical canonical Markdown and request receipts for writes → browser Notes/Calendar, assistant reply, diagram/donut, then browser reload and readback. Compare what appeared on screen with the actual saved state; explicitly verify that chat-only messages create **no** Markdown knowledge and that partial/error cases are not misleading.
- Preserve actor isolation, idempotency and no extra writes across retries, navigation and reload. Use disposable test actor/vault and bounded model calls; do not touch PROD or real personal records. A browser using fake provider replies does **not** satisfy the real-model acceptance gate.
- **Pi arm64 Chromium dependency trap:** The downloaded Puppeteer Chromium binary can fail with missing `libatk-1.0.so.0` and related `ldd` dependencies despite being cached. Before declaring Chromium unavailable, check `ldd` and reuse only the existing vetted locally staged runtime libraries, when present, under `/home/ragdehl/projects/.odyssey-agent-runs/e6-chromium-runtime-deps/root/usr/lib/aarch64-linux-gnu` by setting a **process-local** `LD_LIBRARY_PATH` for the test command. Never install system packages or globally alter loader paths to fix an isolated test. Confirm Chromium starts, and record which dependency boundary was exercised.
- **Chromium secure-origin trap for user clicks:** Odyssey generates schema confirmation IDs with `crypto.randomUUID()`, unavailable to browsers on an internal `http://172.18.x.x` origin. A live n8n service can therefore return real previews while the browser blocks confirmation with «No se ha podido crear un identificador seguro». Do **not** weaken ID generation. Use the real HTTPS/Access path when authenticated, or an exact-operation-allowlisted `http://127.0.0.1` reverse proxy that forwards unmodified operations to real DEV n8n (localhost is a trusted browser context), documenting that it is **not** external Cloudflare authentication. Navigate visibly to Notas before clicking a schema editor button, then await both feature-status hydration and note-list render; hidden DOM elements and immediate snapshots are not representative clicks. After schema confirmation, distinguish `queued` from **active**: check one HTTP confirmation, the managed runtime restart, new schema revision/type/field readback **from the real browser** and byte-for-byte vault integrity. Remove temporary DEV-only feature flag overrides and archive any synthetic-only schema test state after the run.
- **DEV public-route drift trap:** `python3 scripts/odyssey_dev_public_routes.py status --machine` may report `DRIFT` when a newly imported browser module such as `/api/schema-model.js` has not been added to the actual DEV Cloudflare route contract. Do not bypass `odyssey-dev deploy`'s public-route guard, and do not treat a general 'test this' authorization as the **separate explicit consent** needed for `--authorized-dev-change` of Cloudflare. Run isolated real Chromium UI tests and authenticated HTTP tests meanwhile; label the actual deployed-app journey unverified until DEV ingress is aligned and a pinned deploy has succeeded.
- Record screenshots/DOM observations, test phrases and outcomes, trace/request IDs, pinned deployed SHA, provider vs fake status, Markdown before/after where relevant, failures and timing. **If authenticated browser interaction or any required vertical stage was not actually exercised, report `APP E2E NOT VERIFIED` and keep the feature unaccepted**, even when all unit tests and CI are green. Do not silently label lower-level checks as end-to-end.
- **WorkSession performance trials must preserve real browser presence.** `odyssey_web/presence.js` sends authenticated `active`, `heartbeat`, and `inactive` signals to `/api/conversation`, warming local embeddings during Chat hydration. Any test proxy that responds with a fake `200`/`ignored_test_presence` yields a deliberately **cold or unrepresentative** run; do not compare it as normal UX. For realistic tests allowlist and forward the typed presence payload to actual DEV n8n/runtime, confirm the upstream acknowledgment and note worker warmup state, then measure from actual form submission. Record cold/warm separately; worker RSS is a hint, not proof of model readiness. Keep the session, test actor, synthetic-request allowlist, no PROD routing and byte-for-byte Markdown check. Treat browser favicon 404 as an optional static miss, not a runtime error; never suppress real n8n/request failures.

For paid provider evidence first read `odyssey-live-provider`. For status and tests see `docs/architecture/functional-roadmap.md`, `docs/architecture/testing.md` and `scripts/odyssey_dev_browser_readonly.cjs`.
