# Diagnose the existing Odyssey product before changing it

1. **Reproduce and locate the failing boundary.** Capture the exact user-visible symptom and request/actor-scoped `status`, `product_outcome`, stage results, errors, checkpoint sequence, and E3 receipt. State what ran and what did **not** run; don't infer a missing entity from a Router failure. Never inspect a private user's vault or print secrets to diagnose.
**Read-only query failures:** a user question may go through `composition.py::execute_hybrid_proven_read` + the existing Core `RetrieveAction` *before* any P4 write/candidate route. Prewrite P4 gate logs are insufficient to diagnose a read-only failure. Inspect the read preflight disposition, provider class/error telemetry, relational Core resolver, actual E2 stages/route and graph/diagnosis projection separately; an empty write-gate log does not prove no user request occurred. Do not inspect the user's private Markdown vault to infer a missing relationship. Do not silently swallow a failed read preflight and then blame the fallback Router; record only safe error category and observed stage. Never derive source-specific code from an example question.
2. **Inventory existing owners first.** Search `AGENTS.md`, `.codex/skills`, the active roadmap, existing Issues/PRs, and the live path across Router, Temporal, Core, E2 graph/ledger, C4 diagnostic, n8n and frontend. Verify feature flags and deployed SHA separately from the working-tree SHA. Search for a feature that already handles this class (e.g. canonical identity selection, pending clarification, error diagnosis, replay recovery) **before** building an alternative.
3. **Explain why it did not engage.** Trace gating conditions, error code/outcome, stage sequence, schema parsing, presentation, and persistence across the actual call chain. Check disabled switches, missing evidence, earlier abstention, transport or renderer rejection, stale deployment and actor mismatch. Differentiate missing functionality from a broken connection or test that skips the step.
4. **Repair the owner, not the example.** Prefer reusing/fixing the existing capability. Avoid exact text, person names, hardcoded failure categories, duplicated routers, new buttons and separate state machines without a justified general contract. Preserve semantic authority: Router routes; Core owns identity and planned facts; E3 alone authorizes/records writes; C4 diagnoses from verified stages but is never itself permission to write or blindly retry. For model work read `odyssey-llm-stage` and validate real semantics with a bounded provider gate before adoption.
5. **Prove the missing boundary end to end.** Add a failing regression showing why the original path was bypassed, an independent normal-case regression and adversarial no-write/replay cases. Run focused tests, cross-surface gate, and authenticated user-style E2E using a disposable actor. Separate recorded vs live GPT and source vs deployed commit. Invite independent review and preserve FAIL findings after corrections until rechecked.
6. **Close with evidence.** Report *what existed*, *why it was skipped*, *minimal shared fix*, *what remains unverified*, and how the new test guards against repeating this failure. Update the existing architecture owner rather than creating another implementation or vague policy. If the issue is a recurring agent failure, also use `odyssey-skill-steward`.

Trigger examples: "we already implemented that but it doesn't work"; "why does Odyssey say clarify even though it knows my family?"; a Router refusal hidden by n8n; repeated patchwork despite green CI. Non-trigger: ordinary new feature with no observed failure; use `odyssey-start-work` and the feature skill instead.
